# Phase 2 Review and Update

## What was wrong in V2.1
1. The Maven project used H2 while the SQL schema was MySQL; the runtime configuration therefore did not exercise the intended database.
2. `Product` used `name` while the MySQL table uses `product_name`, so the entity did not match the schema.
3. The controller exposed JPA entities directly and there was no service layer.
4. Only Product had a real backend entity; the database contained the rest of the QMS domain without corresponding Java implementation.
5. `data.sql` targeted a singular `product` table and omitted the required `productCode` column.
6. The frontend called `/api/batches` although no Batch controller/entity was present in the supplied source.
7. Automation contained only one smoke feature and no reliable multi-module coverage.

## Phase 2 changes
- MySQL-first Spring Boot configuration using `pharmapack_app`.
- Entity/repository/service/controller layers for Product and Batch.
- Core module implementations for Material, Equipment, Packaging Lines, Production, AQL, Reconciliation, QA Review, Deviation and CAPA.
- Fetch/entity-graph usage for read endpoints that include relationships; Batch uses DTO responses to avoid Hibernate lazy-proxy serialization failures.
- Global API error response.
- React forms for Product and Batch plus module navigation foundation.
- Cucumber/REST Assured smoke coverage for major API areas.
- Database migration and app-user scripts.

## Phase 2.1 test-pass fixes (this update)
This pass installed MySQL 8.0 and Node in the review environment and actually executed what could be executed there (`database/*.sql` against a live server, `npm run build` for the frontend). Maven Central was blocked by the sandbox's egress policy, so `mvn clean test` / `mvn -f automation/pom.xml test` still could not be run directly here; the backend/automation fixes below come from a careful line-by-line comparison of the Cucumber features, step definitions, repositories and schema rather than a live test run. Please run the full `RUNBOOK.md` sequence locally to get the final confirmation.

1. **`automation/.../features/smoke.feature` used step text with no matching definition** (`Given the API is running`, `When I request products`, `Then the response is successful`) — every other feature used differently-worded steps that *were* defined. With `cucumber-junit-platform-engine`, undefined steps fail the build, so this scenario failed on every run. Added matching step definitions to `ApiSteps.java` instead of rewriting the feature.
2. **`database/phase2-migration.sql` used `CREATE INDEX IF NOT EXISTS`, which is not valid MySQL syntax** (MySQL has no `IF NOT EXISTS` clause on `CREATE INDEX`). The script aborted on its second line and none of the five indexes it defines were ever created. Rewrote it using `information_schema.statistics` checks + `PREPARE`/`EXECUTE`, so it creates each index once and is safe to re-run. Verified against a live MySQL 8.0.46 instance, including running it twice back-to-back.
3. **`frontend`: `npm run build` failed with 100+ TypeScript errors** — `@types/react`/`@types/react-dom` were never added to `package.json`, and there was no `vite/client` type reference for the CSS import. Added both dev dependencies and `src/vite-env.d.ts`. Also fixed a real type error: `useEffect(load, [])` was passed an `async`-returning function, which `EffectCallback` disallows; wrapped it as `useEffect(() => { load() }, [])`. `npm run build` now completes cleanly (verified in this environment).
4. **Latent `LazyInitializationException` risk on several list endpoints.** `open-in-view` is disabled (correctly, for a real app), and `QAReviewController`, `DeviationController`, `ReconciliationController`, `CapaController`, `AqlController` (`/inspections`) and `ProductionController` (`/runs`, `/runs/{id}/entries`) return JPA entities with lazy `@ManyToOne`/`@OneToOne` associations straight from the controller. The existing `@EntityGraph` hints only fetched one level deep (e.g. `batch`), but `Batch.product` is itself lazy, so serializing a populated row would still throw once it tried to render the nested `product`. This doesn't fail today only because `seed.sql` leaves those tables empty. Extended every relevant `@EntityGraph` to include the nested path (e.g. `batch.product`, `deviation.batch.product`) and added one to `CapaRepository`, which had no entity graph at all. This keeps the current GET-based Cucumber suite green and also makes those endpoints safe once records exist in them (e.g. after exercising the module forms or writing further POST-then-GET tests).
5. Removed the stale `target/` build output and `frontend/node_modules`/`dist` before repackaging, since they no longer match the edited sources.
6. **`automation/pom.xml` was missing `org.junit.jupiter:junit-jupiter-api`.** `ApiSteps.java` statically imports `org.junit.jupiter.api.Assertions.*` (`assertEquals`, `assertTrue`), but the POM never declared that artifact and nothing else on the classpath pulls it in transitively (`cucumber-junit-platform-engine` and `junit-platform-suite` only bring in the JUnit *Platform* modules, not *Jupiter*). This surfaced once `mvn -f automation/pom.xml test` actually ran against real Maven Central (`package org.junit.jupiter.api does not exist`, plus three `cannot find symbol` errors for the assertion methods) — a pre-existing bug in the original file that this sandbox couldn't catch without network access. Added `org.junit.jupiter:junit-jupiter-api:5.11.0` (test scope), version-aligned with the `junit-platform-suite:1.11.0` already in the POM.

## Phase 2.2 — closed the remaining POST-response gap
The Phase 2.1 gap note below (kept for history) has been addressed: `QAReviewController`, `DeviationController`, `ReconciliationController`, `CapaController`, `AqlController` and `ProductionController` now follow the same pattern `BatchController`/`BatchResponse` already used, for **both** their `GET` and `POST` handlers, not just `GET`:
- Added a flat response record per module — `QAReviewResponse`, `DeviationResponse`, `ReconciliationResponse`, `CapaActionResponse`, `AqlInspectionResponse`, `ProductionRunResponse`, `ProductionEntryResponse` — each carrying the parent batch's `batchId`/`batchNumber`/`productCode`/`productName` (and, where relevant, the related deviation/plan/line/equipment) as plain fields instead of nested lazy entities.
- Every repository's `save()`-then-return path now refetches through an `@EntityGraph`-annotated `findById` (added where missing: `QAReviewRepository`, `DeviationRepository`, `CapaRepository`, `AqlInspectionRepository`, `ProductionEntryRepository`; `ProductionRunRepository` already had one) before building the DTO, so a `POST` response can no longer hit a lazy, session-less association the way it could before.
- `Deviation.batch` and `CapaAction`'s derived batch/product fields are nullable-safe in the DTO mapping, matching the schema (`deviations.batch_id` has no `NOT NULL` constraint).
- `ReconciliationController.calculate()` no longer reassigns `batch` on every call (only when creating a new row), and now returns via the existing entity-graph `findByBatchId` instead of the entity it was about to save.

This was reasoned through and written the same way as the Phase 2.1 backend fixes (no Maven Central access in this sandbox to compile it), so please run `mvn -f automation/pom.xml test` (with the backend up) and a couple of manual `POST` calls (e.g. `POST /api/qa-reviews`, `POST /api/deviations`) to confirm on your machine — the automation suite's assertions (status/content-type only) won't change, but the response bodies now look like `{"id":1,"batchId":2,"batchNumber":"BATCH-DEMO-001","productCode":"PMP-001",...}` instead of a raw, potentially-lazy entity graph.

## Phase 2.4 — real bug caught by the new automation coverage: production runs never set line_id
Confirmed on the user's machine: after fixing the Eclipse/Lombok environment issue (see note below), `GET /api/batches` returned correct flat JSON and `mvn -f automation/pom.xml test` went from 8 failures down to **1** — every module except Production. That one remaining failure was a real, pre-existing backend bug that the new `production.feature` POST scenario (added in Phase 2.3) was the first test ever to exercise:

- `production_runs.line_id` is `NOT NULL` in `database/schema.sql`, and `ProductionController.RunCreate` already accepted a `lineId` field in its request body — but `ProductionController.run()` never used it. It built the `ProductionRun` with only `.batch(b)`, so every `POST /api/production/runs` failed with `Column 'line_id' cannot be null`, regardless of what the caller sent. The frontend's Production-run form (added in Phase 2.3) had the same gap — it only ever sent `batchId`.
- Fixed `ProductionController.run()` to look up the `PackagingLine` via `lineId` (required — throws `IllegalArgumentException("lineId is required")`/`"Packaging line not found"` the same way the existing `batchId` validation does) and the optional `Equipment` via `equipmentId`, and to set both on the builder.
- Fixed `frontend/src/main.tsx`: added `PackagingLine`/`Equipment` types, loads `/api/master/lines` and `/api/master/equipment` alongside the other module lists, and the Production Run form now has a required Line selector and an optional Equipment selector, both sent in the POST body. `npm run build` re-verified clean (0 TypeScript errors) after this change.
- Fixed `automation/.../features/production.feature` to send `"lineId":1` in its POST body (packaging line seed data has ids 1/2 — `LINE-01`/`LINE-02`) and added an assertion that the response's `lineCode` field is present.

This is exactly the kind of bug the Phase 2.3 coverage expansion was meant to catch — it was invisible before because the Production module previously had zero automation coverage and the frontend form for it didn't exist yet either. Please re-run `mvn -f automation/pom.xml test` (backend up) to confirm **19/19, 0 failures**, and re-check the Production tab in the UI (Line is now a required field when starting a run).

**Separately, an environment note for anyone hitting `"Unresolved compilation problems"` as a runtime 500 error:** this project's entities use Lombok (`@Getter @Setter @Builder`). If the backend is run from Eclipse's own "Run" button rather than `mvn spring-boot:run` in a terminal, and Lombok isn't installed into that Eclipse instance, Eclipse's compiler (ECJ) silently fails to generate the Lombok-based accessor methods and replaces them with a runtime-throwing stub — every entity method looks "undefined" at runtime even though the source is correct and `mvn` compiles it fine from the command line. The fix is either to always run the backend via `mvn spring-boot:run` from a terminal, or to install Lombok into Eclipse (`java -jar lombok.jar` downloaded from projectlombok.org, pointed at the Eclipse installation, then a full Eclipse restart).

This is a portfolio/training implementation and is not a validated GMP production system.
